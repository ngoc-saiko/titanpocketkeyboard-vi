  <action>
    FIX-05 per REQUIREMENTS.md: deleteLength must correctly handle multi-character Telex replacements without leaving remnants.

    Current logic (line 460): `val deleteLength = minOf(replacementLength, textBeforeCursor.length - lastSpaceIndex - 1)`. Two hazards:
    1. When there is no preceding space, lastSpaceIndex == -1, so `textBeforeCursor.length - (-1) - 1 = textBeforeCursor.length` — acceptable, but confirm it never yields a negative or over-count for a word at buffer start.
    2. replacementLength is derived from the NEW replacement string length (adjusted by isReverseTone), but the number of characters to DELETE should equal the length of the OLD text being replaced (the previous composed form), not the new form. When a multi-character composed form (e.g. a diacritic vowel that displaced 2 typed chars) is replaced, using the new length can leave a remnant or over-delete.

    Fix: compute deleteLength as the count of characters of the CURRENT word-fragment that the new replacement supersedes, clamped to the available characters after the last space. Concretely: keep the minOf clamp against `textBeforeCursor.length - lastSpaceIndex - 1` (the count of chars in the current word before the cursor) so it can never over-delete past the word boundary, and ensure the delete count matches what was actually on screen for the fragment being replaced (account for the isReverseTone case where one appended original char must remain). Guard `deleteLength` to be non-negative before calling deleteSurroundingText (the existing `if (deleteLength > 0)` at line 462 already prevents a zero/negative delete; ensure the computed value cannot exceed the on-screen fragment length). Add a brief comment citing FIX-05 explaining the bound.

    Do NOT change sendCharacter or the isReverseTone semantics; scope the change to the deleteLength computation and its clamp so no stale characters remain and no characters beyond the current word are deleted.
